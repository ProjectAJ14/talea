### `talea sync`

Clones what is missing, fast-forwards what is there. Safe to run unattended, and safe to run twice.

What it will **not** do, and this is the whole of it:

- **It will not merge a divergence.** Fast-forwards only. Anything else is reported for you to deal with.
- **It will not move you off your branch.** It fast-forwards the branch you are *on*, or leaves it alone and says why. A branch with no upstream is fetched and left.
- **It will not touch a dirty repo.** Uncommitted changes mean it fetches and stops, with a line saying so.
- **It will not push.**

Every command runs **from anywhere**. Inside a workspace, that workspace. Outside one, the workspace `talea init` made — and if this machine has several, it asks which. With no terminal to ask on (a script, a pipe) it lists them and exits non-zero rather than picking one for you.

```bash
talea sync -g nonstopio      # one group
talea sync eklavya           # one repo — same as -r eklavya
talea sync --no-clone        # fast-forward only, clone nothing
talea sync --no-adopt        # skip the existing-checkout scan
```

`talea clone` is the first half on its own — clone what is missing and never fetch or merge. It is what you want on a slow connection.

### `talea status`

| Column | What it shows |
|---|---|
| `REPO` | repository name |
| `BRANCH` | the branch checked out right now |
| `DEFAULT` | the repo's default branch, blank when you are already on it |
| `STATE` | clean or dirty, and commits ahead or behind origin |

```bash
talea status --drift         # only repos on some other branch
talea status --missing       # only repos not cloned yet
talea status --all           # the whole catalogue, not just this machine
```

### `talea prune`

Worktrees pile up. Each one carries its own `node_modules`, `build` or `.dart_tool`, so thirty forgotten ones can hold gigabytes long after their branches were merged. `talea prune` finds them — in every repo this machine keeps, including worktrees that live outside the workspace — and gives each exactly one verdict:

| Verdict | Means | With `--apply` |
|---|---|---|
| `merged` | every commit is on `origin/<default branch>`, or an identical change is (a rebase merge); a merge commit only if it is the merge git would make by itself | removed |
| `missing` | the folder is already gone | the record is cleared |
| `dirty` | modified or untracked files | kept |
| `ignored` | merged, but holds ignored files that are not build output, like a `.env` | kept, unless `--with-ignored` |
| `nested` | merged, but a repo inside its folder holds work of its own — a linked worktree, uncommitted changes, a stash, or a commit no remote has | kept |
| `unreadable` | talea could not read all of it — a folder it may not open, a git call that failed | kept |
| `unused` | a branch with no commits of its own, cut more than a day ago | removed |
| `fresh` | the same, cut within the last day — a task just started | kept |
| `locked` | `git worktree lock`ed | kept |
| `unmerged` | anything else | kept |

```bash
talea prune                  # the plan, with sizes; changes nothing
talea prune --apply          # do it
```

`fresh` and `unused` show the branch's age beside the verdict (`fresh · 7h`). A lock is kept unless Claude Code left it: it locks each agent's worktree with `claude agent <id> (pid N start <time>)`, and once that process has exited the worktree is judged as if unlocked, marked `· stale lock`, and `--apply` unlocks it before removing it. Any other lock is never touched. The dim line under a locked row shows its reason.

The removal is `git worktree remove`, never forced, so git itself refuses a tree with uncommitted work. **The branch is kept** — only the folder goes, and `git worktree add` brings it back. git deletes ignored files without asking, so a worktree holding ones that are not build output is kept as `ignored` and the plan names them. Move them out, or add `--with-ignored`. A file byte-identical to the main checkout's copy at the same path does not count — it survives the removal — and a folder of ignored files is judged file by file, so a `.claude/` holding only a seeded settings file keeps nothing.

Build output does not count either. talea ships a list of it — `node_modules`, `build`, `.dart_tool`, Flutter's `ephemeral/` and `Generated.xcconfig`, `*.iml`, `.idea/` and more — in [`src/regenerable.gitattributes`](https://github.com/ProjectAJ14/talea/blob/main/src/regenerable.gitattributes), written in git's own attributes syntax and matched by git itself. A new ecosystem is a new line there, not new code. A pattern for every repo on your machine goes in git's global attributes file (`git config --global core.attributesFile`), and a repo takes one of talea's back with `-talea-regenerable`.

A repo inside a worktree is judged by what it holds, not where it sits. `flutter build ios` leaves clean SwiftPM clones under `build/`, and those do not keep a merged worktree. A linked worktree, uncommitted changes, a stash or a commit no remote has does, and the verdict says which (`nested · 1 dirty`), with the repo named underneath. A clean one's own ignored files are judged like the worktree's, wherever it sits: a `.env` in a clone under `build/` keeps the worktree, even though `build/` itself is build output.

Nothing talea cannot read counts as safe. A folder the walk may not open, or a git call that fails, keeps the worktree as `unreadable`, and the plan names where. With `--apply`, each worktree is judged again just before it goes, so an ignored file written or a nested repo changed since the plan keeps it too — and with `--with-ignored`, only the ignored files the plan named may go with it.

A file a build copies out of tracked source — a generated page in `public/`, say — sits under no build folder, and the main checkout's copy is only as fresh as its last build. Mark it in the repo's `.gitattributes` and it stops counting:

```
web/public/runtime.html talea-regenerable
generated/** talea-regenerable
```

The mark is read from origin's default branch as well as the worktree's own, so adding it today covers worktrees branched before it. A mark only this machine should keep goes in `.git/info/attributes` instead. Mark only what a build really writes: a marked file is deleted with the folder, and a broad pattern like `**` switches the guard off for that repo.

Each row names the worktree by its folder; the full path sits dimmed on the line below it, ready to copy.

A merge commit on the branch counts as merged only when its result is the merge git would make from its two parents by itself. One that adds a change of its own — a hand-resolved conflict, a file added mid-merge — is work origin may not have, and reads as `unmerged`.

A **squash merge** reads as `unmerged`: the squashed commit is a new change, not the ones on the branch, and telling them apart would take asking GitHub. Remove those worktrees yourself. A repo with no default branch recorded is skipped — run `talea discover`.

### `talea where`

```bash
talea where eklavya          # the absolute path, one line, nothing else
cd $(talea where eklavya)    # what it is actually for
talea where                  # the workspace root
```

The path goes to stdout on its own, so it composes with `cd`, `code`, `open` and anything else that takes a directory. Every diagnostic goes to **stderr**, and an unknown name **exits non-zero** — so `cd $(talea where typo)` fails rather than landing you in your home directory.

If two owners have a repo of the same name it says so and exits non-zero rather than picking one. Pass `owner/name`.

### Changing what this machine keeps

```bash
talea add some-repo          # keep one more here, and clone it now
talea rm some-repo           # take it off the list
talea select                 # reopen the whole checklist
talea pick some-repo         # keep that one — an unknown name opens the checklist
```

`talea rm` removes the repo from this machine's list and **leaves the checkout exactly where it is**, printing the path. Deleting it is your call — `rm -rf` already exists for when you mean it.

`talea select` opens the checklist with your current selection ticked. Everything in the catalogue is listed, including archived repos and forks: this machine is allowed to keep something the default set does not have. `--no-clone` saves the list without filling it.

`talea pick <name>` is `talea add` when the name matches exactly one repo — case does not matter, and `owner/name` works. When it matches none, or two owners share it, the checklist opens instead, so a typo lands you in the list rather than on an error.

### Running one command everywhere

```bash
talea exec -- git log --oneline -1
talea exec -g nonstopio -- npm install
talea exec --all -- git branch --show-current
```

Everything after `--` is the command, run once per repo with that repo as the working directory. Repos are processed one at a time so the output stays readable and attributable.

### Exit codes

Every bulk command exits **non-zero if any repo failed**. Per-repo errors are printed and the run keeps going, so without checking the exit code a partial failure reads as success to a script. A *skip* is not a failure — a `sync` over a workspace you are working in still exits 0.
