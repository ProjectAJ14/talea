Three files, and confusing them is how this tool would go wrong.

| File | Holds | Travels |
|---|---|---|
| `<workspace>/talea.repos.json` | a catalogue for this tree only | no |
| `~/.talea/talea.repos.json` | **your** catalogue — what `discover` writes | yes, through the gist |
| `<workspace>/.talea.json` | what **this machine** keeps, and what it has moved | **never** |

**Nearest catalogue wins.** A `talea.repos.json` sitting next to a workspace beats the one in your home directory. The catalogue packaged with talea is last, and ships empty on purpose — a published package carrying the author's repo list would be a personal tool wearing a general one's name.

### A catalogue entry

```json
{
  "name": "eklavya",
  "owner": "ProjectAJ14",
  "url": "git@github.com:ProjectAJ14/eklavya.git",
  "defaultBranch": "main",
  "group": "ProjectAJ14",
  "default": true,
  "fork": false,
  "pushedAt": "2026-09-21T18:02:11Z"
}
```

| Field | Owned by | Meaning |
|---|---|---|
| `name`, `owner` | GitHub | identity |
| `url` | you | where to clone from |
| `defaultBranch` | GitHub | recorded per repo, because GitHub is the only thing that knows. A repo with none is cloned on whatever the server hands over — never on an assumed `main` |
| `group` | you | the folder it lives in. Falls back to `owner`, then to `repos` |
| `dir` | you | an explicit folder name, when the repo name is not the one you want |
| `default` | you | whether a **brand new** machine starts with it ticked |
| `ignore` | you | nothing touches this checkout, ever |
| `fork`, `pushedAt`, `archived` | GitHub | facts, refreshed by `discover` |

### Why the selection is a list of repos

`.talea.json` holds `selected`, and it is a list of repos, written `owner/name` — not a filter over `default: true`.

A filter would re-evaluate on every run, so adding `default: true` to a repo in the shared catalogue would silently start cloning it on every machine you own. The catalogue does not get to make that decision.

It names the owner because two of the accounts discovery reaches can each have a repo of the same name, and keeping one is not keeping both. A list written before talea recorded owners holds bare names; each still counts while only one repo in the catalogue has that name. Once two do, neither is kept and every run says so, until `talea add <owner>/<name>` settles which — or `talea rm <name>` drops the entry when you want neither. An ignored or `missing` entry with the same name does not count: neither can be kept, so the name still means the one live repo.

`selected` being **absent** and being **empty** are different things. Absent means "never asked" and falls back to the catalogue defaults; empty means "I chose nothing", and is respected.

### The gist

```bash
talea manifest push             # publish; prints the id on the first run
talea manifest pull <gist-id>   # link this machine and fetch
talea manifest where            # which file is in use, and which gist
```

The id is remembered in `~/.talea/state.json`, so later pushes and pulls need no argument.

:::caution
The gist is private. It still holds the names of your private repositories, so treat the id like a bookmark you would not paste into a public channel.
:::

Only the catalogue is published. What each machine keeps stays in that machine's `.talea.json` and never leaves it.

### What a catalogue may say

A catalogue travels — through the gist, from a teammate, as a file in a team repo — so talea treats it as input and checks it before any command reads a path out of it, and before `manifest pull` writes one over yours:

- **Paths stay below the workspace.** A repo's `name` and `owner` are single folder names. Its `group` and `dir`, and a group's `dir`, are relative paths like `work/api`. An absolute path, a `..`, a `.`, a backslash, a drive letter or an empty part (`work/`) is refused. On Windows, so is a name ending in a dot or a space — Windows drops them, so `app.` is `app` — or one it reserves, like `CON` or `AUX`; on macOS and Linux those are ordinary names.
- **Fields have the types talea reads.** `name` is required text; `owner`, `url` and `defaultBranch` are text; `default`, `ignore`, `archived`, `fork` and `missing` are `true` or `false`. Fields talea does not know are left alone.
Each problem is named with its entry and field — `repos[3] (acme/app): "dir" has a part that is ".."` — and every command refuses the file until it is fixed, because no command can safely read a path out of it.

**No two repos share a folder.** Two repos that would land in one folder — two owners' `app` in one group — or one inside the other, clash until one gets a `dir` of its own. Neither case nor Unicode spelling counts: macOS and Windows treat `App` and `app`, and the two ways of writing `café`, as one folder. A clash is checked by the commands that place checkouts — `clone`, `sync`, `adopt`, `add` — before they start, and only for the repos that run would place, so `list`, `where` and a sync of other repos still work. `discover` and `manifest pull` name a clash when they write one. An `ignore: true` repo is placed by nobody, so it clashes with nothing.

The spelling is not the whole check. Right before a move, a clone or a group doc is written, the real destination is resolved through every symlink above it, and anything that would land outside the workspace is refused. A workspace that is itself a link to another drive is fine; a group folder inside it that links somewhere else is refused, so keep repos on another disk by moving or linking the whole workspace there. A `CLAUDE.md` that is itself a symlink is treated as yours and never written through.

:::caution
A catalogue still decides **which repositories you clone, from which URLs, and where inside the workspace they land**. talea clones with git's own defaults, which run nothing from the repository, but a catalogue can point you at any repo. Read one you did not write before you sync it.
:::

### Groups are just folders

A group is the directory a repo lives in, resolved in this order: an explicit `group` field, then the repo's `owner`, then `repos`. Two owners can be consolidated into one group by giving both sets of entries the same `group`.

Group folders are created when a repo is cloned into them, not up front — an empty directory for a group this machine keeps nothing from is noise.
